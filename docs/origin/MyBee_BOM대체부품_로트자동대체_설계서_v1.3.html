대체 부품원본 대신 써도 된다고 설계가 승인한 부품(mbdev.bom_substitute).승인되지 않은 부품은 규격이 같아 보여도 자동으로 쓰지 않는다.
로트 단위 대체작업지시 하나(= 생산 로트 하나)의 한 자리를 전량 대체 부품으로 바꾸는 것.로트 안에서 원본과 대체를 섞지 않는다 — 섞으면 리콜 때 어느 제품에 무엇이 들어갔는지 가를 수 없다.
필요일부품이 라인에 있어야 하는 날 = 상위 제조 계획 오더(작업지시가 될 것)의 계획 착수일. 완제품은 MPS 기간의 시작일.확보 예정일과 비교하는 기준.
확보 예정일이 작업지시 몫까지 부품을 손에 넣을 수 있는 날. 재고 → 미입고 발주(납기) → 새 발주(조달 기간) 순으로 계산.더 살 수 없는 부품(단종 · 최종 구매일 경과)은 확보 예정일이 없다(NULL).
누적 순소요같은 부품을 여러 작업지시가 원할 때 필요일이 빠른 작업지시부터 재고와 발주를 채워 가며 계산하는 방식.「재고 1,000개」가 작업지시 셋에게 각각 1,000개로 보이는 착시를 막는다.
조달 기간지금 발주하면 들어오기까지의 일수(vendor_buying_terms.lead_time_days, 승인 공급사 중 가장 짧은 것).재고 · 발주로 못 채울 때 확보 예정일 = 오늘 + 조달 기간.
재귀 쿼리 (WITH RECURSIVE)자기 자신을 다시 부르는 SQL. BOM 처럼 「부품 안에 부품」이 몇 단인지 모를 때 끝까지 내려간다.PostgreSQL 표준 기능. 별도 그래프 DB 없이 원본 DB Table 에서 바로 전개한다(설계방향서 v2.4).

하위 단계 번호 (LLC)모든 BOM 에서 한 품목이 나오는 가장 깊은 단계(완제품 0).같은 부품을 여러 제품이 쓰면 그 소요를 한 단계에 모아 한 번에 차감하려는 순서. 이 순서로 풀어야 재고가 두 번 잡히지 않는다.

중복 실행 방지 (idempotency)같은 요청이 두 번, 세 번 들어와도 결과가 한 번 처리한 것과 똑같게 만드는 성질. 예를 들어 신청서 제출 버튼을 두 번 눌러도 신청은 하나만 생기고, 통신이 끊겨 시스템이 같은 요청을 다시 보내도 돈이 두 번 나가지 않는다.왜 필요한가 — 네트워크는 끊기고, 시스템은 답이 없으면 다시 보내고, 사람은 버튼을 두 번 누른다. 이 세 가지는 막을 수 없으므로 두 번 와도 안전하게 만든다.
중복 실행 방지 키 (중복 실행 방지 키)같은 요청인지 가리는 열쇠. 이 열쇠가 같으면 새로 처리하지 않고 먼저 처리한 결과를 그대로 돌려준다. 예) 프로젝트 신청의 열쇠는 「회사 + 신청번호 + 개정차수」다 — 같은 신청서를 두 번 보내도 신청은 하나다.열쇠는 업무적으로 뜻이 있는 값으로 만든다. 시각 · 난수 · 재시도 횟수 · 서버 이름처럼 매번 달라지는 값은 넣지 않는다. 넣으면 두 번째 요청이 「다른 요청」이 되어 중복이 생긴다.
되돌릴 수 없는 일 (non-idempotent)이체 · 발송 · 신고처럼 한 번 나가면 되돌리기 어려운 일. 이런 단계는 중복 실행 방지 키를 반드시 두고, 답이 없으면 다시 보내지 않고 조회해서 결과를 확인한다.답이 없는 상태를 「모름」으로 두고 사람이 확인하게 한다. 다시 보내는 것이 가장 위험하다.

업무코드는 새로 만들지 않는다. 대체 지정은 설계(D01)가, 로트 단위 판정은 MRP(D15 FL0015001)가, 확정 · 적용은 제조(D06)가 기존 업무코드 안에서 맡는다. 업무코드당 단계가 3 ~ 8개로 정해져 있고 FL0001022 는 이미 8단계이므로, 새 동작은 이미 있는 규칙 · 기록 · 승인 단계에 넣었다 — 실행 수단 · 단계 수 · 처리 순서가 그대로라 등록표 수치(스킬 756 · 도구 744 · 단계 3,837)도 바뀌지 않는다. 이 표의 내용은 업무스킬설계서 D01 v1.5 · D06 v1.6 · D10 v1.5 · D15 v1.8 · D16 v1.5 와 실행순서 v2.9 에 실었다.
