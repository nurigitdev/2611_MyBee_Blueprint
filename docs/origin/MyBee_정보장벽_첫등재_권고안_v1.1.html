용어 정의

용어 정의 — 이 문서에서 쓰는 말

「버전」은 버전, 데이터베이스의 표는 DB Table, 「중복 실행 방지」은 중복 실행 방지로 부른다(설계지시문 19.1.4).

버전 (version)문서 · 기준 · 정의가 고쳐질 때마다 매기는 번호. v1.0 → v1.1 처럼 올라간다. 예전 문서에서 「버전」이라고 부르던 것을 이 문서부터 버전으로 부른다.옛 버전은 고치지 않고 그대로 두고 새 버전을 따로 낸다. 그래야 그때 무엇을 보고 결정했는지 나중에 되살릴 수 있다.
DB Table데이터베이스에 실제로 만들어지는 표. 예) mbproj.project_request. 예전 문서에서 그냥 「표」라고 부르던 것을 DB Table 로 부른다.문서 안에서 읽으라고 그린 표(비교표 · 목록표)는 그대로 「표」라고 부른다. 둘을 섞지 않는다.
중복 실행 방지 (idempotency)같은 요청이 두 번, 세 번 들어와도 결과가 한 번 처리한 것과 똑같게 만드는 성질. 예를 들어 신청서 제출 버튼을 두 번 눌러도 신청은 하나만 생기고, 통신이 끊겨 시스템이 같은 요청을 다시 보내도 돈이 두 번 나가지 않는다.왜 필요한가 — 네트워크는 끊기고, 시스템은 답이 없으면 다시 보내고, 사람은 버튼을 두 번 누른다. 이 세 가지는 막을 수 없으므로 두 번 와도 안전하게 만든다.
중복 실행 방지 키 (중복 실행 방지 키)같은 요청인지 가리는 열쇠. 이 열쇠가 같으면 새로 처리하지 않고 먼저 처리한 결과를 그대로 돌려준다. 예) 프로젝트 신청의 열쇠는 「회사 + 신청번호 + 개정차수」다 — 같은 신청서를 두 번 보내도 신청은 하나다.열쇠는 업무적으로 뜻이 있는 값으로 만든다. 시각 · 난수 · 재시도 횟수 · 서버 이름처럼 매번 달라지는 값은 넣지 않는다. 넣으면 두 번째 요청이 「다른 요청」이 되어 중복이 생긴다.
되돌릴 수 없는 일 (non-idempotent)이체 · 발송 · 신고처럼 한 번 나가면 되돌리기 어려운 일. 이런 단계는 중복 실행 방지 키를 반드시 두고, 답이 없으면 다시 보내지 않고 조회해서 결과를 확인한다.답이 없는 상태를 「모름」으로 두고 사람이 확인하게 한다. 다시 보내는 것이 가장 위험하다.
업무코드회사의 일을 더 쪼갤 수 없는 단위로 나눠 붙인 코드. 예) FL0012001 프로젝트 신청. 사람이 하든 에이전트가 하든 같은 코드로 부른다.모든 일은 업무코드로 수행되고, 보상 · 원가 · 기록이 모두 이 코드에 붙는다.
업무영역업무코드를 묶는 큰 분류. D01 HW개발 … D18 감사 · D19 프로젝트기획·생성 · D20 지식관리(2026-09-29 신설) — 모두 20개.코드 안의 두 자리(FL0019001)가 업무영역이다.
스킬 · 도구 · 규칙업무코드를 수행하는 세 가지 수단. 스킬은 AI 가 문장을 읽고 쓰는 일, 도구는 계산 · 서식 · 외부 연결처럼 정해진 대로 도는 프로그램, 규칙은 조건과 결론을 표로 적어 둔 판정.수치와 판정은 도구와 규칙이 한다. AI 는 수치를 만들지 않는다.
PA · IA · EA · TA · VAPA 는 프로젝트를 맡는 에이전트(프로젝트 1개에 1개), IA 는 사람의 말을 알아듣고 업무로 잇는 에이전트, EA 는 법무 · 회계 같은 전문가 의견을 내는 에이전트, TA 는 외부 시스템을 부르는 에이전트, VA 는 결과를 검증하는 에이전트.외부로 나가는 일은 TA 만 한다.
자율 수준 L1 · L2 · L3에이전트가 사람 없이 어디까지 갈 수 있는지. L1 은 사람이 결정, L2 는 에이전트가 하되 사람이 승인, L3 는 에이전트가 하고 사람은 나중에 본다.위험이 큰 업무일수록 낮은 수준을 쓴다.
NVT 토큰업무를 수행하면 쌓이는 회사 안의 점수. 연말에 단가를 곱해 인센티브 · 연봉에 반영된다.직책이 아니라 수행한 업무에 붙는다.
채택 보상금제안이 채택되었을 때 제안자에게 한 번 주는 보상. 직원은 토큰으로, 외부 제안자는 현금으로 받는다. 상한 500만 원.가결(직원) 또는 용역 계약 체결(외부) 때 지급한다.
사업화 성과 보상제품 · 서비스가 실제로 팔린 뒤 해마다 나누는 보상. 연간 순매출의 0 ~ 3% 안에서 위원회가 정한다.제안 20% · 원 기여 30% · 진행 기여 50% 로 나눈다. 진행 기여는 해마다 다시 계산한다.
판정 기준 버전문턱 값 · 요율 · 가중치처럼 나중에 바뀔 수 있는 숫자를 화면이나 규칙 본문에 박지 않고 따로 모아 둔 것. 예) PRJ-ECON(경제성) · PRJ-RESEARCH(조사) · PRJ-REWARD(보상).값이 바뀌면 새 버전을 게시하고, 지난 판정은 그때 버전으로 다시 볼 수 있다.
개정차수한 신청서를 고쳐 다시 낼 때 올라가는 번호. 제출한 개정차수는 고치지 않고 새 개정차수를 만든다.중복 실행 방지 키의 한 조각이기도 하다.
관리 최소집합모든 프로젝트에 반드시 담기는 D12 업무코드 5건(개설 · 업무 구성 확정 · PM 지정 · 진행 보고 집계 · 종결).빼거나 바꿀 수 없다.
게이트다음 단계로 넘어가려면 통과해야 하는 관문. 이 문서에서는 G-1 등재 · G0 아이디어 · G1 기획 · G2 신청 · G3 심의 · G4 착수.게이트마다 무엇을 확인하는지 정해 둔다.
사전 조사신청 전에 에이전트가 하는 조사. 시장 조사(시장 규모 · 경쟁 동향)와 소요 비용 조사(개발 기간 · 단계별 비용) 두 가지다.조사는 에이전트가 하고, 채택은 사람이 승인한다.
TAM · SAM · SOM시장 크기를 세 겹으로 본 것. TAM 은 품목 전체 시장, SAM 은 우리가 닿을 수 있는 시장, SOM 은 실제로 가져올 수 있는 몫(하단 · 상단).편익의 판매 수량은 SOM 하단을 기본으로 쓴다.

1. 결론

한 줄. 첫 등재는 「새면 되돌릴 수 없고 법이 막는 것」부터 좁게 한다 — ① 미공개중요정보 ② 내부감사 · 조사 ③ 경쟁 관계 고객의 제안 · 수주 ④ 인사 민감(급여 · 징계 · 연봉) 네 가지를 1순위로 협업 도입 1단계 전에 게시하고, ⑤ 외부 제안 심사 ⑥ 법적 보존 · 분쟁 ⑦ 고객 전담 · 핵심기술은 해당 사안이 생길 때 등재한다. 기본은 NO_MIX(섞지 않음)이고, 겸직 금지(NO_DUAL_MEMBERSHIP)는 계약 · 법이 전담 인력을 요구할 때만 쓴다.

왜 프로젝트 이름이 아니라 유형으로 권고하나. MyBee 는 설계 단계라 운영 중인 프로젝트 목록이 없다. 그리고 1,000 테넌트 SaaS 라 회사마다 프로젝트가 다르다. 그래서 플랫폼은 기본 장벽 틀 7종과 후보를 찾는 조회를 함께 내고, 각 회사의 준법 · 법무 책임자가 운영 시작 때 조회 결과를 보고 FL0013036 협업 허용 정책 확정으로 게시한다. 장벽은 IA 가 스스로 만들지 않는다 — 사람이 게시한 것만 작동한다.

2. 등재 기준 — 셋 중 둘이면 등재

기준묻는 것예
① 되돌릴 수 없는가한 번 섞이면 회수 · 원상복구가 안 되는가미공개 실적이 다른 프로젝트 대화에 인용됨 · 경쟁사 제안 가격이 다른 고객 제안에 반영됨
② 법 · 계약이 막는가법령 · 비밀유지 계약 · 고객 계약이 분리를 요구하는가자본시장법 미공개중요정보 · 영업비밀(부정경쟁방지법) · 개인정보 · 공익신고자 보호 · NDA 의 전담 인력 조항
③ 같은 사람이 양쪽에 있을 수 있는가인력이 적어 한 사람이 양쪽에 참여할 가능성이 실제로 있는가영업 담당 한 명이 경쟁 고객 둘을 맡음 · 재무 담당이 결산과 투자 검토에 모두 참여

③ 이 없으면(양쪽 인력이 완전히 다르면) 장벽이 작동할 일이 없다 — 이미 프로젝트 권한(참여)이 막는다. 장벽은 한 사람 안에서 섞이는 것을 막는 장치다(12.16.3).

3. 첫 등재 대상 7종

#대상 프로젝트구분 · 범위 · 방식끝나는 때게시 책임순위

B-7고객 전담 · 핵심기술 프로젝트 — 고객이 전담 인력을 계약으로 요구 · 국가핵심기술 · 수출통제 대상OTHER · PAIR 또는 ONE_TO_ALL · NO_DUAL_MEMBERSHIP(계약 · 법이 요구할 때만)계약 종료 + 비밀유지 기간정보보안(D13)3
왜 이 넷이 1순위인가. B-1 은 새면 거래 제한 · 형사 문제가 되고(자본시장법 제174조), B-2 는 조사 정보가 피감 쪽으로 새면 증거가 훼손되고 신고자가 드러난다. B-3 은 한 고객의 가격 · 사양이 다른 고객 제안에 들어가면 영업비밀 · NDA 위반이다. B-4 는 급여 · 징계 · 평가 정보가 다른 프로젝트 대화에 섞이면 개인정보 사고이며, IA 1:1 대화를 가장 많이 쓰는 사람(인사 · 재무 담당)이 바로 여러 프로젝트에 참여한다. 넷 모두 기준 ① ② ③ 을 다 충족한다.

상장 여부에 따라 B-1 을 달리 둔다

4. 운영 시작 때 후보를 찾는 조회

각 틀마다 이미 설계에 있는 원장에서 후보 프로젝트를 뽑는다. 조회 결과는 후보일 뿐이고, 게시는 FL0013036 의 사람 확인을 거친다. 아래 SQL 은 설계 예시이며 DBMS 에서 실행하지 않았다.

틀후보를 찾는 원장조건
B-1mbir.pr_ir_event · mnpi_register · mnpi_holdermnpi_candidate = true 이거나 등재 상태가 공시 전인 사안의 source_project_id
B-2mbiaud.audit_engagement · investigation진행 중 감사건 · 조사건의 프로젝트
B-3mbsal.opportunity · proposal · mbproj.project_member제안 · 협상 단계(PROPOSAL · NEGOTIATION)에 동시에 있는 서로 다른 고객의 기회 쌍 중 같은 사람이 양쪽에 참여한 쌍 — 고객끼리 경쟁 관계인지는 영업 담당이 확인한다(아래 주의)
B-4mbproj.project(운영 프로젝트) × 업무코드급여 계산 · 연봉 결정 · 징계 · 평가 업무코드를 담은 운영 프로젝트
B-5mbproj.external_proposal_intake · proposal_agreement심사 중 외부 제안과 주제가 겹치는 내부 과제(사전 조사 유사도 · 담당 조직 같음)
B-6mbiaud.investigation_evidence · mbqua.customer_claim법적 보존(legal_hold_at)이 걸린 증거의 프로젝트 · 분쟁 상태의 고객 클레임 프로젝트
B-7mbsal.proposal(nda_contract_no · confidentiality) · 계약NDA 에 전담 인력 조항이 있거나 기밀 등급 SECRET · 특수 표지(핵심기술 · 수출통제)가 붙은 프로젝트
-- B-3 경쟁 고객 제안 쌍 후보 — 제안 · 협상 단계가 겹치고 같은 사람이 양쪽에 참여한 쌍(기준 ③)
WITH live AS (
  SELECT o.project_id, o.party_code, o.opportunity_no, o.stage, o.expected_close_date
    FROM mbsal.opportunity o
   WHERE o.stage IN ('PROPOSAL', 'NEGOTIATION')
),
pairs AS (
  SELECT a.project_id AS project_a, b.project_id AS project_b, a.party_code AS client_a, b.party_code AS client_b
    FROM live a JOIN live b ON a.project_id < b.project_id AND a.party_code <> b.party_code
),
shared AS (
  SELECT pr.project_a, pr.project_b, pr.client_a, pr.client_b, count(DISTINCT ma.employee_id) AS shared_people
    FROM pairs pr
    JOIN mbproj.project_member ma ON ma.project_id = pr.project_a AND ma.left_at IS NULL
    JOIN mbproj.project_member mb ON mb.project_id = pr.project_b AND mb.left_at IS NULL AND mb.employee_id = ma.employee_id
   GROUP BY pr.project_a, pr.project_b, pr.client_a, pr.client_b
)
SELECT s.* FROM shared s
 WHERE NOT EXISTS (SELECT 1 FROM mbauth.info_barrier b                     -- 이미 게시된 장벽은 뺀다
                    WHERE b.valid_to IS NULL AND ((b.project_a_id, b.project_b_id) IN ((s.project_a, s.project_b), (s.project_b, s.project_a))))
 ORDER BY s.shared_people DESC;
-- 결과는 「같은 사람이 동시에 맡은 서로 다른 고객 제안」까지다. 두 고객이 경쟁 관계인지는 영업 담당이 표시하고 FL0013036 의 사람 확인으로만 게시한다
주의 — 설계에 「고객끼리의 경쟁 관계」 칸이 없다. 외부 당사자 자격 심사의 competitor_check 는 외부 제안자가 우리의 경쟁사인지를 보는 칸이라 고객 A · B 가 서로 경쟁하는지는 알려 주지 않는다. 그래서 B-3 후보 조회는 「같은 사람이 동시에 맡은 서로 다른 고객의 제안」까지만 뽑고, 경쟁 여부는 영업 담당이 표시한다. 표시가 반복되면 외부 당사자의 확장 칸(ext)에 산업 · 경쟁 묶음을 메타데이터로 두는 것을 다음 개정 후보로 둔다(DB Table 변경 없이).

5. 첫 등재에서 하지 않는 것

하지 않는 것이유
모든 프로젝트 사이에 장벽협업이 멈춘다. 장벽은 기준 셋 중 둘을 충족할 때만 — 과차단은 사람들이 IA 밖(메신저 · 메일)으로 우회하게 만들어 오히려 새는 길이 된다
같은 고객의 여러 프로젝트같은 고객 안에서는 정보가 오가는 것이 정상이다. 고객 계약이 프로젝트 사이 분리를 요구할 때만 B-7
부서 사이 장벽장벽은 프로젝트 단위다. 부서 경계는 프로젝트 참여 · 권한이 이미 막는다
IA 가 장벽을 스스로 만들기IA 는 후보를 보일 수는 있어도 게시할 수 없다(판정 기준은 사람이 게시 — 8.7). 장벽이 잘못 걸리면 업무가 멈추기 때문에 책임자가 있어야 한다
처음부터 겸직 금지인력이 적은 회사에서 겸직 금지는 업무를 세운다. NO_MIX 로 시작하고, 계약 · 법이 요구하거나 NO_MIX 위반이 실제로 나올 때만 올린다

6. 첫 등재 절차와 일정

주할 일누가끝났다고 보는 기준

2FL0013036 협업 허용 정책 확정으로 장벽을 게시한다 — 위험 높음 · 사람 승인준법 책임자 승인info_barrier 게시 · 기준 버전

점검주기보는 것
