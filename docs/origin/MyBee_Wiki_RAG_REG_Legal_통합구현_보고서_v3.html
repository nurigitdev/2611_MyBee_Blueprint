01

최선의 기본값은 근거 중심 작성 독립 검증

먼저 믿을 수 있는 원문을 확보하고, 중요한 주장마다 근거를 연결한 뒤, 계산·실행·원문 대조로 확인하십시오. 온톨로지와 지식 그래프는 이 과정에서 반복되는 용어 혼동과 관계 검색 실패를 해결할 때 추가하는 것이 합리적입니다.

이 보고서의 종합 제안

모든 업무에 보편적으로 가장 우수하다고 입증된 단일 기술은 없습니다. 여기서 ‘최선’은 중대한 오류가 최종 결과에 남을 가능성을 낮추면서, 검토 비용과 처리시간을 감당할 수 있는 구성을 뜻합니다. 근거가 부족할 때 확인되지 않은 결론을 보류하는 능력도 품질에 포함합니다.

무엇을 토대로 썼는가

공식 자료·승인된 내부 자료·실제 코드와 데이터를 확인하고, 원문 위치와 적용 시점까지 남깁니다.

어떻게 맞는지 확인했는가

문장별 원문 대조, 수치 재계산, 테스트 실행, 법적 요건 검토처럼 결과물에 맞는 확인 수단을 사용합니다.

어디까지 알 수 있는가

사실·추론·가정을 구분하고, 근거 부족·충돌·미실행 상태를 표시합니다. 중요한 미해결 사항은 제출 전에 해소합니다.

먼저 투자할 순서

① 출처와 버전 관리 → ② 검색·원문 확인 → ③ 주장별 근거표 → ④ 분야별 검증과 보류 기준 → ⑤ 평가자료 구축 → ⑥ 필요한 범위의 온톨로지·지식 그래프.

범위: 일반 문서·소프트웨어 코드·법률검토의 작성 방법을 다룹니다. 개별 사건의 법률 판단이나 특정 제품의 성능 인증은 포함하지 않습니다. 실험 수치는 해당 연구 시점·대상·평가 정의에만 적용하며, 현재 제품 성능으로 일반화하지 않습니다.

06

그래프를 도입한다면 출처 있는 연결 을 만드십시오

그래프의 실무 가치는 어떤 근거를 따라 결론에 도달했는지 추적하고, 흩어진 관계를 재사용하는 데 있습니다. 개념 체계와 실제 사실, 사람이 확정한 관계와 AI가 제안한 관계를 구분해야 합니다.

설명용 가상 사례 · 실제 법령이나 판례가 아닙니다

개정 전 발생한 사건에 어떤 조항을 검토해야 하는가

[사건 X 발생일: T1] → 검토 후보 → [규정 A / v1 적용 기간: T0~T2] ← 개정 관계 ← [규정 A / v2 시행일: T2]

[부칙 Y 경과조치 원문] → 적용 범위 확인 → [주장 C 조건부 결론]

온톨로지는 ‘사건·규정 버전·시행일·경과조치’의 의미를 정하고, 그래프는 구체적 연결을 저장합니다. 검색은 연결된 원문을 가져오고, 검토자는 부칙과 사실관계가 적용 결론을 뒷받침하는지 확인합니다.

날짜만 비교해 법 적용을 확정하지 않습니다. 경과조치·소급 적용 문제·행위 유형 등 필요한 조건을 원문과 함께 검토해야 합니다.

OWL은 일반적으로 정보가 없다고 곧 거짓으로 보지 않는 ‘열린 세계’ 가정을 따릅니다. 필수 근거가 누락됐는지를 검사하는 일은 별도의 SHACL·스키마·업무 규칙으로 설계해야 합니다. [3][4] 논리적으로 일관된 데이터라도 현실과 다를 수 있습니다.

그래프 검토가 유리한 경우

• 여러 계약·주체·규정을 따라가는 질문이 반복된다.

• 동일 대상의 별칭·합병·버전 관계 때문에 오류가 생긴다.

• 관계의 출처와 변경 이력을 유지할 담당자가 있다.

• 같은 자료·모델로 비교했을 때 관계 질의의 성능 개선이 확인된다.

기초 작업이 먼저인 경우

• 소수 문서의 단순 요약이 대부분이다.

• 원문 품질·버전·접근 권한부터 정리되지 않았다.

• 오류 대부분이 수치 계산이나 코드 실행에서 발생한다.

• 그래프를 만드는 비용은 잡았지만 갱신·검토 비용은 없다.

법률 예외의 처리: ‘원칙 → 결론’만 연결하면 예외가 빠질 수 있습니다. 예외·조건·경과조치를 함께 보관하고 충돌은 덮어쓰지 않습니다. 단순한 그래프 경로를 법률 추론의 완결된 증명으로 취급하지 않는 것을 권장합니다.

07

문서 코드 법률은 마지막 검증이 다릅니다

분야별 실무 제안

A 보고서 제안서 일반 문서

1. 사실 목록부터 분리: 날짜·이름·수치·외부 주장과, 제안·평가·예시를 구분합니다. 창작 예시에는 실제 사실처럼 보이지 않게 표시합니다.

2. 원문을 단위까지 확인: 표의 분모·대상 기간·통화·각주를 보존합니다. OCR로 가져온 수치와 인용문은 원본을 대조합니다.

3. 수치는 재계산: 증가율·합계·환산은 계산식과 입력을 남깁니다. 수치가 맞아도 비교 집단이 다르면 해석을 수정합니다.

4. 주장별 출처 확인: 링크가 열리는지와, 그 링크가 문장을 지지하는지는 별도로 검사합니다. 출처가 서로 같은 원자료를 재인용한 것인지도 확인합니다.

5. 마지막 편집 후 재대조: 문장을 매끄럽게 고치면서 ‘일부’를 ‘모두’로, ‘가능성’을 ‘확정’으로 바꾸지 않았는지 확인합니다.

권장 완료 조건: 핵심 사실·수치의 원문과 계산 경로가 확인되고, 추정·제안·가상의 표시가 유지되며, 중요한 반대 근거와 누락이 설명되어 있을 것.

B 소프트웨어 코드 기술 문서

1. 실제 프로젝트가 기준: 현재 코드, 의존성 잠금 파일, 실행 환경, 버전에 맞는 공식 문서를 읽습니다. 함수·옵션·패키지의 실재 여부를 확인합니다.

2. 요구사항을 관찰 가능한 동작으로 표현: 입력·출력·오류 처리·경계 조건을 정하고, 버그 수정이면 가능한 경우 기존 실패를 먼저 재현합니다.

3. 범위를 좁혀 구현: 기존 인터페이스·규칙을 유지하면서 요청된 동작을 구현합니다. 관련 없는 대규모 변경은 검토 부담을 늘립니다.

4. 성격에 맞는 검사: 빌드·타입·정적 분석과 함께 정상·실패·경계·통합 시나리오를 확인합니다. 검사 강도는 변경 위험과 영향에 맞춥니다.

5. 테스트의 정답도 검토: 생성한 코드를 그대로 따라 쓰는 테스트 대신 요구사항·기존 계약·독립적인 예상 결과를 사용합니다. 통과를 위해 기대값을 임의 변경하지 않습니다.

6. 실행 증거를 남김: 대상 버전, 환경, 수행한 검사, 결과, 미검사 영역을 기록합니다. 실행할 수 없으면 ‘미실행’으로 전달합니다.

권장 완료 조건: 필요한 검사에서 요구 동작과 회귀 여부가 확인되고, 변경 설명이 실제 차이와 일치할 것. 테스트 통과는 검사하지 않은 모든 상황의 안전성을 증명하지 않습니다.

코드 평가의 참고 사례인 SWE-bench는 실제 저장소 이슈에 대한 수정 결과를 평가합니다. 본 보고서는 공개 순위를 모델 추천이나 사용자 프로젝트의 성공률로 전용하지 않습니다. [14]

C 법률검토 계약검토

법률 실무 보강 실제 사례와 요건별 작성 예시는 13장에 수록했습니다.

1. 관할과 시간축 확정: 국가·적용 법체계·사실 발생 시점·검토 기준일을 구분합니다. 계약 원문, 변경 합의, 당사자 주장, 입증 자료를 나눕니다.

2. 쟁점과 요건 분해: 질문을 법적 쟁점으로 나누고, 각 요건에 필요한 사실과 입증 자료가 있는지 표로 확인합니다.

3. 공식 원문 확보: 한국 법령은 국가법령정보센터에서 본문·연혁·시행일·부칙을 확인하고, 판례는 법원 공식 서비스의 원문을 대조합니다. [15][16]

4. 인용 정확성 검사: 사건번호·법원·선고일·쟁점·판시 내용이 일치하는지 확인합니다. 요약문이나 검색 결과만으로 결론을 확정하지 않습니다.

5. 적용 가능성과 반대 근거 검토: 유리한 판례만 찾지 말고 사실관계 차이, 반대 판단, 후속 판단, 개정·폐지·경과조치를 확인합니다. 외국 법의 효력 판단 체계를 한국 법에 그대로 옮기지 않습니다.

6. 사실 → 규범 → 적용 → 결론: 사실 확인과 법적 해석을 분리하고, 결론의 전제 및 추가 확인 사항을 기재합니다.

7. 중대한 판단은 담당 전문가 확인: 권리·의무·제출 문서에 영향을 주는 결론은 관련 원문과 근거표를 함께 검토할 수 있도록 전달합니다.

‘없는 판례를 만들지 않기’와 ‘맞는 판례를 적용하기’는 별도 과제입니다.

4. 자동 평가를 표본 대조: AI 채점이 맞는지 사람이 확인하고 불일치 유형을 기록합니다. 법률처럼 중요한 분야는 전문가가 핵심 판단 기준을 정합니다.

5. 변경 시 재평가: 모델·검색 설정·문서 구조·온톨로지·원문이 바뀌면 관련 사례를 다시 확인합니다. 알려진 오류는 회귀 평가에 추가합니다.

합격 기준은 ‘증명된 무오류’와 다릅니다.

‘확인되지 않은 핵심 인용이 있으면 제출 보류’ 같은 운영 기준을 둘 수 있습니다. 평가 표본에서 중대 오류가 0건이어도 전체 업무에서 발생 확률이 0이라는 뜻은 아닙니다. 표본 수·업무 분포·불확실성을 함께 보고합니다.

“입증책임”은 막연히 원고 또는 피고라고 자동 배정하지 않습니다. 청구원인·항변과 적용되는 실체법·절차법을 조사하여 근거와 함께 기록합니다. 불리한 자료가 발견되면 삭제하지 않고 그 영향을 설명합니다. 검토가 끝나지 않은 쟁점을 매끄러운 단정문으로 바꾸지 않습니다.

초안과 원문 검사를 분리하기

초안 작성 후 검사자는 주장별로 원문을 직접 엽니다. 작성 모델의 요약만 재사용하면 같은 오류를 반복할 수 있습니다. 별도 모델은 누락 후보와 모순을 찾는 보조 수단으로 쓰고, 사실·인용은 원문 대조로, 숫자·날짜는 규칙이 확인된 계산으로, 법적 적용은 담당자의 검토로 확인합니다. 소규모 업무에서도 같은 사람이 원문을 다시 대조하는 별도 검토 단계를 둡니다.

최종 편집이나 번역 뒤에는 인용과 조건부 표현을 다시 검사합니다. “검토가 필요하다”가 “적법하다”로 바뀌거나, 부정어·단서·예외가 빠지는 편집 오류도 차단 대상입니다.

5 한국법 실습에서 조건부 결론 작성하기

다음 네 사례의 당사자, 기록 번호와 사실관계는 모두 가상입니다. 실제 의뢰인의 사건이나 실제 국내 판결 사례가 아닙니다. 문안은 내부 검토 또는 협상용 예시이며 대괄호의 빈칸은 제출 전에 확인해야 할 사항입니다. 법률 설명과 보고서가 제안하는 계약 조건을 구별해 표시했습니다.

실습 1 납품 지연을 이유로 한 계약 해제 검토

가상 상황 구매자는 납품 기한을 지키지 못한 공급자와의 계약을 즉시 해제하는 통지서를 원합니다. E01 계약서와 E02 납품 기록은 있으나, E03 독촉 이메일의 도달 여부와 추가 이행기간이 명확하지 않습니다. 공급자가 이행을 확정적으로 거절했는지도 확인되지 않았습니다.

문제 문안 “납기 위반 사실이 있으므로 계약은 즉시 적법하게 해제되며 모든 손해를 배상해야 한다.” 이 문장은 해제권 발생, 행사와 도달, 손해배상 요건을 검토 없이 한 번에 확정합니다.

확인한 법률 민법 제544조는 이행지체 시 상당한 기간을 정한 이행 최고와 그 기간 내 미이행을 전제로 해제를 규정하고, 사전의 명확한 이행거절에 관한 예외를 둡니다. 2026년 3월 17일 시행본을 확인했습니다. 이 조문만으로 개별 계약의 즉시 해제와 모든 손해의 배상을 인정할 수는 없습니다. [L3]

추가 확보 계약서의 해제·해지 특약과 변경합의, 실제 납품·검수 기록, 구매자의 협조와 대금 의무 이행 자료, 독촉 내용과 도달 자료, 이행거절을 뒷받침할 원문을 확보합니다.

검토 순서 의무와 이행기 특정 → 지체 관련 사실 → 최고 및 예외 → 특약과 다른 적용 규정 → 의사표시의 내용과 도달 → 반환·손해배상 등 효과를 별도로 검토합니다. 계속적 계약의 해지와 해제를 혼용하지 않습니다.

수정 문안 예시 “제공된 자료상 약정 납기 미준수 여부는 E01과 E02를 대조하여 확인할 필요가 있습니다. 민법 제544조에 따른 해제를 검토할 경우, 이행 최고와 상당한 기간의 경과 또는 최고가 필요 없는 예외에 관한 사실이 중요합니다. E03의 도달과 부여 기간이 확인되지 않아 현재 자료만으로 즉시 해제가 유효하다고 확정하기 어렵습니다. 계약 특약과 쌍방의 이행 상황을 추가 확인한 후 최고 통지 또는 해제 통지의 문안을 결정할 것을 제안합니다.”

사용 기준 통지서 발송 전에 담당 변호사가 해제 근거와 통지 문구를 승인하고, 수신인·도달 방식·요구기간을 확정합니다. 내부 의견의 유보 문구를 제거해 확정적 외부 통지로 바꾸는 일은 별도의 판단입니다.

실습 2 해고예고수당만으로 해고가 유효하다는 오류

가상 상황 사용자는 1년간 근무한 근로자에게 해고예고수당을 지급하고 즉시 퇴직시키는 문서를 요청합니다. 상시 근로자 수·근로자성·해고 사유·보호기간과 취업규칙 절차에 대한 자료는 불완전합니다. 아래는 관련 조항의 적용이 확인된다는 전제의 검토 예입니다.

문제 문안 “30일분 임금을 지급하면 정당하게 즉시 해고할 수 있다.” 금전 지급 문제를 해고 전체의 적법성으로 확대하는 오류입니다.

확인한 법률 근로기준법 제23조는 해고 등에서 정당한 이유와 일정한 해고금지 기간을 다루고, 제26조는 원칙적으로 30일 전 예고 또는 30일분 이상의 통상임금 지급 및 예외를 규정합니다. 제27조는 해고 사유와 시기의 서면통지 및 그 효력을 다룹니다. 세 조문의 검토 항목을 분리해야 합니다. 확인본은 2026년 8월 20일 시행본입니다. [L4] [L5] [L6]

실습 3 행정소송 기간의 잘못된 자동 계산

가상 상황 행정처분에 불복하려는 의뢰인이 이메일로 알게 된 날과 처분서 수령일을 서로 다르게 말합니다. 처분 문서의 원본과 송달 기록은 없고, 행정심판을 거쳤는지도 불명확합니다.

문제 문안 “행정소송은 언제나 처분일부터 90일 이내에 제기하면 된다.” 소송 유형과 기간의 출발점을 혼동합니다.

확인한 법률 행정소송법 제20조는 취소소송에서 처분 등을 안 날부터 90일을 규정하고, 일정한 행정심판 경유 상황에는 재결서 정본 송달일부터 계산하도록 정합니다. 별도로 처분 등 또는 해당 재결부터 1년의 제한과 정당한 사유 예외를 두고, 90일 기간은 불변기간으로 규정합니다. 2026년 5월 12일 시행본을 확인했습니다. [L7]

먼저 분류 취소소송·무효확인·부작위 등 검토할 절차를 특정하고, 관련 특별법, 행정심판과 전심절차의 적용 여부를 조사합니다. 모든 행정 분쟁에 위 조문을 그대로 적용하지 않습니다.

기산일 확인 처분서·송달 증명·이메일 원문·심판 청구 및 재결 문서를 확보하여 “안 날”, “처분이 있은 날”, “재결서 정본 송달일” 후보를 구별합니다. 서로 다른 후보를 조용히 하나로 합치지 않습니다.

계산 검증 담당자가 적용 기간과 기산점을 승인한 뒤 초일 산입 여부, 말일 처리, 휴일, 특별규정 등 관련 기간 계산 규칙을 추가 확인하여 계산합니다. 달력 프로그램의 덧셈 결과만으로 법정 기한을 확정하지 않습니다.

수정 문안 예시 “현재 자료로는 불복 절차와 기산점을 확정할 수 없습니다. 취소소송을 검토한다면 행정소송법 제20조와 해당 특별법의 적용 여부를 확인해야 합니다. 처분 인지일과 송달일에 관한 진술이 일치하지 않으므로 처분서와 송달 자료를 우선 확보하고, 확인될 수 있는 이른 기산일을 기준으로 기한 보전 조치의 필요성을 담당 변호사가 즉시 검토해야 합니다.”

기한 관리표의 필드 절차명 / 적용 조항과 버전 / 기산 사건 / 후보 날짜 / 증거 / 계산 규칙 / 잠정 만료일 / 불확실성 / 승인자 / 확인일. 후보 날짜가 비어 있으면 가상의 제출 마감일을 생성하지 않습니다.

실습 4 개인정보 처리위탁 계약의 범위 혼동

가상 상황 고객정보를 처리하는 서비스 제공자가 “처리위탁 계약”이라는 제목의 약정을 보내면서, 고객정보를 자사 AI 학습에도 이용할 수 있다는 조항을 제안합니다. 실제 처리 목적, 재위탁 업체와 처리 국가, 보유기간은 충분히 밝혀지지 않았습니다.

문제 문안 “처리위탁 계약만 체결하면 모든 이용과 국외 처리가 허용된다.” 계약 제목만으로 법적 성격과 요건을 확정한 오류입니다.

확인한 법률 개인정보 보호법 제26조는 위탁 시 문서에 의한 목적 외 처리 금지와 보호조치 등을 규정하고, 공개·감독 및 재위탁 동의 등의 사항을 다룹니다. 확인본은 2026년 9월 11일 시행본입니다. 실제 업무가 위탁인지 별도 목적의 처리인지 판단하고, 제공·국외 이전 등 다른 규율을 추가 조사해야 합니다. [L8]

확인 자료 개인정보 항목·정보주체·처리 목적·지시권·저장 국가·접근자·재위탁 업체·학습 이용·삭제와 백업 정책을 데이터 흐름표로 받습니다. 계약서와 실제 서비스 설정이 일치하는지 대조합니다.

협상용 조항 예시 “수탁자는 별지 [업무 및 개인정보 목록]에 정한 업무와 위탁자의 적법한 지시 범위에서만 개인정보를 처리한다. 수탁자의 독자적 모델 학습 또는 별도 목적 이용은 허용하지 않으며, 이를 추진하려면 별도 법적 요건 검토와 계약 변경을 선행한다. 재위탁은 위탁자의 사전 서면 동의를 받아야 한다. 사고 통지는 [협의하여 확정할 기한과 방식]에 따르며, 종료 시 반환·삭제 및 적법한 보관 예외는 별지 [종료 처리 절차]에 정한다.”

문안의 성격 사전 “서면” 동의 방식, 독자적 학습의 계약상 금지와 사고 통지 약정은 이 예시가 제안하는 협상 조건입니다. 법 제26조의 문언 전체를 그대로 옮긴 것이 아닙니다. 사고 통지의 법정 요건·기한, 하위법령상 필수 계약 사항, 국외 이전 등은 별도로 확인하여 약정에 반영해야 하며 이 예시만으로 준법성을 확정하지 않습니다.

결론을 지지하는 핵심 근거가 부족하면 해당 결론을 보류하거나 조건부로 작성하라. 필요한 추가 검색을 제안하되 실시하지 않은 조사를 완료했다고 쓰지 말라.

출력 순서는 핵심 의견, 전제사실과 쟁점, 법적 근거 및 적용 이유 요약, 반대 논거, 문서 초안, 근거표, 미해결 사항으로 하라. 숨겨진 내부 추론 대신 독자가 검증할 수 있는 근거와 적용 이유를 제시하라.

5 수집과 개정 동기화 구현

  1. 등록 자료의 관리 주체, 이용조건, 접근 범위, 원문 주소와 식별자를 등록합니다. 비공개 사건자료와 공통 법률자료는 권한 영역을 분리합니다.
  2. 수집 API 또는 허용된 원문 다운로드 방식으로 확보하고, 원본 해시·수집 시각·응답 상태를 저장합니다. 실패를 빈 문서로 저장하지 않습니다.
  3. 구조 추출 제목·조항호목·단서·부칙·별표·표 머리글을 유지합니다. OCR 원문은 인용하려는 구절을 이미지와 대조합니다.

  5. 검토 AI가 제안한 설명·관계·규칙은 draft로 보관합니다. 규정 책임자 또는 법률 검토자가 실제 원문과 적용 범위를 확인합니다.
  6. 게시와 색인 승인된 revision과 동일한 해시의 청크만 검색에 활성화합니다. 새 색인 묶음이 준비된 뒤 활성 포인터를 전환하여 신구 자료가 섞이는 시간을 줄입니다.

        return "unknown"
    return "satisfied" if review_verified else "unsatisfied"

review_verified는 사용자가 “검토했다”고 입력한 값이 아니라 검토 레코드의 권한·대상·증빙을 서버가 검증한 결과입니다. not_required_by_this_rule는 다른 규정이나 법률에서도 검토가 불필요하다는 뜻이 아닙니다. unknown은 사유와 추가 자료를 화면에 표시하며 자동 승인에 쓰지 않습니다.

위키 편집으로 통제를 바꾸는 경로를 차단합니다. 규칙 본문 수정 → 새 draft revision → 근거·조건 검토 → 테스트 → 권한 있는 승인 → 해당 버전 활성화 순으로 진행합니다. 실행기가 평가하는 규칙은 승인된 내용 해시와 일치해야 합니다. AI와 일반 편집자는 활성 규칙을 직접 수정할 권한을 갖지 않습니다.

8 Wiki Legal과 문서 초안을 연결하는 실제 흐름

예시 A 해고 통지서 작성 요청

가상 요청 “해고예고수당을 주고 오늘 해고하는 통지서를 작성하라.” RAG는 검토 절차와 승인된 통지서 양식을 찾고, REG는 내부 인사 승인과 제출 자료 목록을 점검합니다. Legal은 근로기준법 제23조, 제26조, 제27조의 적용과 사건 사실을 구분하여 검토합니다. 앞의 한국법 실습에서 확인한 원문과 연결하고, 사내 승인 완료를 해고 적법성으로 바꾸지 않습니다.

  1. 사건 저장소에서 근로관계·사업장 적용 범위·사유별 증거·취업규칙·통지 관련 자료를 조회합니다.
  2. Legal 쟁점표에 정당한 이유, 예고, 서면통지, 보호기간 및 기타 적용 쟁점을 각각 기록합니다.
  3. 자료가 부족하면 통지서의 해고 사유를 창작하지 않고 needs_review로 반환합니다.
  4. 검토용 결과에는 초안, 근거별 원문, 내부 승인 미완료, 추가 사실 질문을 함께 표시합니다.
  5. 담당 변호사의 적용 판단과 별도 발송 승인이 완료된 특정 문서 버전만 발송 서비스에 넘깁니다.

예시 B 개인정보 처리위탁 계약 검토

가상 요청 “공급자의 AI 학습 조항을 포함한 위탁계약을 승인해 달라.” RAG는 관련 양식과 업무 설명, REG는 내부 공급자·보안 검토 절차, Legal은 개인정보 보호법 제26조 등 실제 처리 유형에 필요한 법규 검토를 연결합니다. 계약의 제목보다 처리 목적·역할·재위탁·저장 국가 등 사실을 먼저 확인합니다.

만약 내부 규정이 갱신되지 않았거나 법령 적용 시점이 불명확하면 ‘위키 최신 버전이므로 적합’이라고 답하지 않습니다. 사건의 처리 시점과 해당 원문·연혁을 다시 확보하고 관련 해석을 needs_review로 표시합니다. 산출물은 계약 수정안, 그 수정의 법적 근거, 조직이 추가로 요구하는 조건, 협상 가능한 제안을 구분합니다. API 자동 연동만으로 모든 판례와 적용 판단을 확인한 것으로 표시하지 않습니다.

9 권한과 변경 이력을 모든 경로에 적용하기

사용자에게 허용된 자료만 검색·재정렬·프롬프트·답변에 들어가야 합니다. tenant ID와 사용자 ID는 클라이언트 요청값을 그대로 신뢰하지 않고 서버의 인증 결과에서 가져옵니다. 문서 페이지를 막더라도 첨부·임베딩·요약·검색 결과·오류 로그로 내용이 노출되지 않는지 함께 검사합니다. 외부 재정렬 모델을 사용할 때도 자료의 외부 처리 허용 범위를 확인합니다.

PostgreSQL RLS는 행 단위 접근 정책을 구현하는 수단입니다. 공식 문서에 따르면 일반적으로 테이블 소유자와 특별한 권한의 역할은 우회할 수 있으므로, 애플리케이션 계정·테이블 소유자·관리 계정을 분리하고 실제 실행 역할로 검증해야 합니다. [W8] RLS를 켰다는 사실만으로 검색 엔진·파일 저장소·캐시까지 보호되는 것은 아닙니다.

  • 사건 회원, 문서 접근 범위, 원문과 파생 청크의 scope ID를 연결하고 API·검색·첨부 다운로드에서 모두 검사합니다.
  • 복수 근거에서 만든 요약의 읽기 범위는 모든 근거를 읽을 수 있는 사용자 집합의 교집합을 기준으로 합니다. 별도 비식별·공개 승인을 거치면 새 파생 자료로 기록합니다.
  • 캐시 키에는 tenant, 사용자 권한 버전, 사건, 질문 조건, 근거 버전·해시를 포함합니다. 조회 시 현재 권한을 다시 검사하고 권한 회수 시 관련 캐시를 무효화합니다.
  • 관계·인용·검토 이력을 수정할 수 있는 권한도 분리합니다. 위키 설명을 고치는 권한이 법률해석 승인이나 규칙 활성화 권한을 뜻하지 않습니다.
  • 외부 파일의 명령문은 데이터로 취급합니다. 원문 안의 “검증을 생략하라”는 지시가 생성 서비스의 권한이나 완료 기준을 바꾸지 못하게 합니다.

10 개정 때 재검토할 범위를 자동으로 찾기

모든 설명과 출력이 근거 버전을 참조하게 해야 변경의 영향을 찾을 수 있습니다. 다음 연결은 조회용 그래프로 표현할 수 있지만 SQL 관계 테이블로도 구현할 수 있습니다.

원문 버전 S1
  → 근거 연결 E1
  → 위키 해석 I1
  → 사내 통제 규칙 R1 또는 문서 양식 T1
  → 작성 중 초안 D1
  → 특정 버전의 제출 기록 P1

원문 S2 수집 → S1과 차이 확인 → 영향 후보 표시 → 검토 작업 생성
  → I1/R1/T1의 상태 재검토 → 새 승인 버전 → 관련 D1 재검증

P1은 과거 제출 기록으로 보존한다. 이미 제출한 문서를 조용히 바꾸지 않고
수정 또는 후속 조치의 필요성을 담당자가 판단한다.

원문이 바뀌었다고 모든 과거 판단이 틀렸다고 처리하지 않습니다. 편집상 변경, 새 시행일, 실질 규정 변경, 접근 제한을 구분합니다. 영향 분석기는 검토 후보를 찾고, 법적 영향의 최종 판단은 담당자가 기록합니다. 신규 버전의 승인 전에는 영향받는 현재 문서의 제출을 보류하되, 영향 없는 문서는 독립적으로 처리할 수 있게 합니다.

색인 실패·원문 수집 실패·모델 오류는 재시도 가능한 작업으로 관리합니다. 동일 작업의 반복 실행이 중복 초안·중복 승인·중복 제출을 만들지 않도록 idempotency key를 적용합니다. 예를 들어 초안 요청은 사건 ID·요청 해시·근거 묶음 버전으로 식별하고, 외부 제출은 별도 실행 원장으로 중복 여부를 확인합니다.

아래 경로는 이 보고서가 제안하는 내부 API 계약입니다. 현재 존재하는 MyBee API 또는 라이브러리 함수라고 가정하지 않습니다. 개발 시 기존 인증·사건·문서·승인 서비스에 매핑하고, 동일 기능이 있으면 중복 구현하지 않습니다.

원장별 책임 제안 원문 담당자는 수집·버전, 규정 담당자는 사내 통제, 법률 검토자는 해석·적용, 개발 담당자는 검색·규칙 구현, 보안 담당자는 접근 통제를 맡습니다. MyBee의 기존 책임 체계가 있다면 이 기능을 그 체계에 연결합니다. 모델은 후보를 생성할 수 있지만 원문 검증·규칙 활성화·문서 승인 권한을 모두 겸하지 않도록 구성합니다.
